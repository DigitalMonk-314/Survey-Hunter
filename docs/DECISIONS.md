# Survey Hunter — Журнал технических решений

**Версия:** 0.3.0  
**Статус:** Ведение проекта  
**Основной документ:** `ARCHITECTURE.md`

Этот документ фиксирует согласованные технические решения. Изменять их можно после обсуждения и согласования с владельцем проекта.

---

## DEC-001 — Базовый технологический стек

**Статус:** Принято

**Решение:** Использовать Python 3.11+, Telethon, aiogram 3.x, SQLite, aiosqlite, asyncio и PyYAML.

**Причина:** Стек подходит для небольшого асинхронного приложения, отслеживающего публичные Telegram-каналы и отправляющего персональные уведомления.

**Ограничение:** Не добавлять новые инфраструктурные компоненты без обоснованной необходимости.

---

## DEC-002 — Разделение Telegram-клиентов

**Статус:** Принято

**Решение:** Telethon используется для чтения каналов от пользовательского аккаунта. aiogram используется для отправки уведомлений и обработки команд бота.

**Причина:** Эти компоненты выполняют разные задачи и имеют разные способы авторизации.

**Ограничение:** Не смешивать парсинг каналов с логикой отправки уведомлений.

---

## DEC-003 — Асинхронный конвейер обработки

**Статус:** Принято

**Решение:** Использовать `asyncio` и отдельный модуль `pipeline.py` для последовательной обработки публикаций. Для передачи готовых уведомлений использовать `asyncio.Queue`.

**Причина:** Разделение получения сообщений, обработки и отправки уведомлений упрощает сопровождение и обработку ошибок.

**Ограничение:** Не допускать неконтролируемого повторного выполнения операций и повторной отправки уведомлений.

---

## DEC-004 — Хранение данных

**Статус:** Принято

**Решение:** Использовать SQLite через aiosqlite.

**Основные таблицы:**
- `sources` — источники публикаций;
- `messages` — объявления и их статусы;
- `feedback` — действия пользователя.

**Причина:** Для одного пользователя и десяти каналов отдельный сервер базы данных на старте не требуется.

**Ограничение:** Сохранять данные между перезапусками и предусмотреть резервное копирование.

---

## DEC-005 — Фильтрация и скоринг в MVP

**Статус:** Принято

**Решение:** Использовать ключевые слова, извлечение признаков и оценку соответствия профилю из `profile.yaml`.

**Причина:** Правила можно проверять и корректировать на реальных публикациях без внедрения сложных моделей.

**Ограничение:** Не добавлять LLM-классификатор в MVP. Порог оценки должен настраиваться через конфигурацию.

---

## DEC-006 — Обработка ссылок

**Статус:** Принято

**Решение:** Извлекать ссылки из текста, форматирования и доступных URL inline-кнопок.

**Причина:** Рекрутеры могут размещать ссылки не только непосредственно в тексте сообщения.

**Ограничение:** Не требовать обязательного наличия ссылки на Google Forms для каждого объявления.

---

## DEC-007 — Дедупликация

**Статус:** Принято

**Решение:** На первом этапе выявлять точные дубликаты по хешу нормализованного текста и ссылок.

**Причина:** Одно и то же сообщение не должно повторно обрабатываться без необходимости.

**Ограничение:** Не удалять информацию об источниках. Поиск похожих объявлений, размещённых разными рекрутерами, можно добавить после MVP.

---

## DEC-008 — Безопасность секретов

**Статус:** Принято

**Решение:** Хранить токены, API credentials и локальные секреты вне исходного кода.

**Причина:** Утечка авторизационных данных может привести к компрометации аккаунта или бота.

**Ограничение:**
- Не добавлять `.env` и файл сессии Telethon в Git.
- Не публиковать секреты в логах.
- Использовать `.env.example` только как шаблон без настоящих значений.

---

## DEC-009 — Поэтапная разработка

**Статус:** Принято

**Решение:** Реализовывать проект по этапам из `PLAN.md`.

**Причина:** Это упрощает проверку результата и снижает риск накопления ошибок между модулями.

**Ограничение:** Не переходить к следующему этапу без проверки текущего и не менять архитектуру самовольно.

---

## DEC-010 — Отложенные функции

**Статус:** Принято

**Решение:** Гибкие режимы фильтрации, дайджесты, LLM-классификатор, веб-интерфейс, мультипользовательский режим и Docker не входят в обязательный объём MVP.

**Причина:** Сначала необходимо подтвердить работоспособность базового сценария.

**Ограничение:** Не включать отложенные функции в MVP без отдельного согласования.
